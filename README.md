# CSCE 5300 Big Data Project

## Reproduction and Experimental Evaluation of Parallel K-Means for Big Data Clustering

This repository contains the implementation, validation, and experimental framework for a CSCE 5300 Big Data course project based on the research paper:

> **“Big Data Clustering Method Based on Parallel K-Means”**
> Haibo Liu, Yongbin Bai, Zhenhao Chen, and Zhenfeng Zhang
> 2024 IEEE 4th International Conference on Power, Electronics and Computer Applications (ICPECA)

The project focuses on independently reproducing the parallel K-Means architecture described in the reference paper, validating its behavior, and experimentally evaluating its scalability and clustering performance using Apache Spark.

The implementation is being developed incrementally. Each major component is tested independently before being integrated into the complete Parallel K-Means workflow.

---

## 1. Project Objective

Traditional K-Means becomes increasingly expensive as dataset size and dimensionality grow because each iteration repeatedly calculates distances between data points and cluster centers.

The reference paper addresses this limitation by distributing clustering work across Spark partitions and improving the initialization of the global cluster centers.

This project independently implements and evaluates that approach.

The primary research question is:

> **How does parallel K-Means compare with conventional K-Means in execution time, scalability, convergence behavior, and clustering quality as dataset size increases?**

The experimental evaluation will investigate:

- execution time,
- scalability,
- clustering convergence,
- sum of squared errors (SSE),
- clustering quality,
- partition behavior,
- initialization behavior,
- Spark execution configuration,
- and memory behavior where practical.

## 2. Reference-Paper Method

The selected paper proposes an improved Spark-based Parallel K-Means architecture.

The high-level process is:

1. Load and distribute the dataset using Spark.
2. Divide the data across Spark partitions.
3. Perform local K-Means clustering independently inside each partition.
4. Collect the cluster centers generated by the local clustering operations.
5. Re-cluster the collected candidate centers.
6. Use the resulting centers as the initialization for distributed global K-Means.
7. Broadcast the current global centers to Spark workers.
8. Assign distributed data points to their nearest centers.
9. Aggregate cluster statistics.
10. Update the global cluster centers.
11. Repeat until the convergence condition or maximum iteration count is reached.
12. Return the final centers and cluster assignments.

This strategy is intended to provide more stable initialization than selecting global centers randomly while also distributing the expensive assignment calculations across Spark workers.

## 3. Implemented Parallel Architecture

The current implementation follows this architecture:

```text
Raw Feature Vectors
        |
        v
    Spark RDD
        |
        v
+-------------------+
| Spark Partitions  |
+-------------------+
        |
        v
Local K-Means in Each Partition
        |
        v
Local Candidate Centers
        |
        v
Candidate-Center Aggregation
        |
        v
Global Initialization Centers
        |
        v
Broadcast Global Centers
        |
        v
Parallel Point Assignment
        |
        v
reduceByKey Aggregation
        |
        v
Global Center Update
        |
        v
Convergence Check
        |
        +------ Not Converged ------+
        |                           |
        +---------------------------+
        |
        v
Final Centers / SSE / Cluster Counts
```

The implementation is explicit rather than delegating clustering to Spark MLlib's built-in K-Means implementation. This allows the project to examine the distributed operations involved in the algorithm directly.

## 4. Major Implementation Components

### Spark Session Management

The Spark session layer provides controlled creation and shutdown of Spark sessions for demonstrations, tests, and experiments.

Development currently uses Spark local mode.

### Spark Partitioning

The partitioning layer validates how records are distributed across Spark partitions and provides utilities for inspecting partition-level behavior.

### Local K-Means

A deterministic local K-Means implementation is used inside individual Spark partitions.

The local implementation includes:

- input validation,
- squared Euclidean distance,
- nearest-center selection,
- center updates,
- deterministic seeded initialization,
- convergence detection,
- SSE calculation,
- and empty-cluster handling.

### Partition-Level Clustering

Each non-empty Spark partition performs local K-Means independently.

The result from each partition includes:

- local cluster centers,
- local convergence status,
- local iteration count,
- and local SSE information.

These local centers become candidate centers for the global initialization stage.

### Candidate-Center Aggregation

Candidate centers produced by all Spark partitions are collected and clustered again.

This second clustering operation produces exactly `k` centers that are used to initialize distributed global K-Means.

### Distributed Global Iteration

The global iteration performs the distributed assignment and update phase.

Current global centers are broadcast to Spark workers.

Each point is assigned to its nearest center and converted into cluster statistics containing:

- coordinate sums,
- point count,
- and SSE contribution.

Spark `reduceByKey` combines those statistics.

The driver then calculates updated global centers.

### Global Convergence Loop

The distributed iteration is repeated until:

- the convergence tolerance is satisfied, or
- the maximum number of iterations is reached.

The implementation records per-iteration information so that convergence behavior can later be analyzed experimentally.

### Complete Parallel K-Means Pipeline

The complete pipeline connects:

```text
Partition Clustering
        +
Candidate-Center Aggregation
        +
Distributed Global K-Means
```

The returned result includes final clustering information and intermediate metadata needed for experimental analysis.

## 5. Runtime Instrumentation

The pipeline records runtime measurements using Python's monotonic high-resolution performance counter.

Current measurements include:

- partition clustering time,
- candidate-center aggregation time,
- total initialization time,
- iterative distributed global K-Means clustering time,
- final-center evaluation time,
- and total pipeline runtime.

`global_clustering_seconds` measures only the repeated distributed assignment and center-update loop.

`final_evaluation_seconds` measures the separate Spark operation used to calculate final SSE and cluster counts against the returned centers.

The timing relationships are covered by automated tests.

### Controlled Benchmark Timing

A controlled benchmark layer now manages the Spark RDD lifecycle used during experimental execution.

The benchmark process is:

```text
Create RDD
    |
    v
Persist RDD
    |
    v
Materialize RDD with count()
    |
    v
Run Parallel K-Means
    |
    v
Collect Benchmark Metadata
    |
    v
Unpersist RDD
```

Materializing the RDD before the clustering pipeline begins prevents the initial RDD computation from being mixed into the clustering measurements.

The benchmark runner also releases the persisted RDD when execution finishes.

Failure-path cleanup is explicitly tested so that an RDD is unpersisted even when materialization raises an exception.

RDD lifecycle ownership remains in the experiment layer rather than inside the clustering algorithm. This keeps the core algorithm independent from the resource-management policy selected by the caller.

### Important Timing Note

Separating initialization, iterative global clustering, final evaluation, and RDD materialization provides clearer experimental timing boundaries.

The controlled benchmark foundation and repeated scalability experiments have been completed. Six dataset-size/master configurations were measured with three seeds each; the results and their limitations are summarized in Sections 12 and 16.

## 11. Experimental Methodology

The completed controlled scalability study evaluated the custom PySpark Parallel K-Means implementation on deterministic synthetic data. The primary configurations were:

| Parameter | Evaluated setting |
|---|---|
| Dataset sizes | 10,000 and 50,000 records |
| Numerical features | 20 |
| Clusters (`k`) | 5 |
| RDD partitions | 4 |
| Spark masters | `local[1]`, `local[2]`, `local[4]` |
| Measured seeds | 42, 43, 44 |
| Measured repetitions | 3 per configuration; 18 total |
| Global convergence tolerance | `1e-6` (SSE cost-change criterion) |
| Global iteration limit | 100 |

The study varied **dataset size** and **local Spark parallelism** while holding the principal feature, cluster, and partition settings fixed. The local master settings represent different levels of parallel execution on one physical machine; they are not separate cluster nodes.

### Controlled Benchmark Execution

The benchmark framework records configuration metadata, materialized record counts, clustering outcomes, convergence information, SSE, cluster counts, and runtime components. It persists and materializes the input RDD before the measured clustering pipeline and unpersists it after execution, including tested failure paths.

Recorded timing components include partition clustering, candidate-center aggregation, initialization, iterative global clustering, final-center evaluation, and total pipeline runtime.

### Repeated Trials and Comparisons

Three measured seeds (42, 43, and 44) were used for each of the six dataset-size/master combinations. Mean runtime and speedup were calculated relative to `local[1]` at the same dataset size. All 18 measured runs converged.

A conventional K-Means baseline was also evaluated. Because its initialization differs from the parallel approach, differences in clustering quality should be interpreted cautiously rather than as a perfectly controlled algorithm-only comparison.

### Scope of Additional Work

Partition-count sensitivity, KDD Cup 99, clustering purity, memory profiling, and direct numerical comparisons with the reference paper are **not claimed as completed** without verified supporting results. Larger synthetic datasets and additional feature or cluster settings remain possible extensions, not part of the principal verified scalability study.

## 16. Current Experimental Limitations

### Local Spark Execution

The experiments used Spark local mode on one physical computer. `local[1]`, `local[2]`, and `local[4]` vary local parallelism but do **not** represent a multi-node Spark cluster. The measured speedups therefore demonstrate **local parallel scalability**, not the multi-machine performance of the reference paper.

### Dataset Scope and Partitioning

The principal verified scalability experiments used deterministic synthetic datasets with 10,000 or 50,000 records, 20 numerical features, five clusters, and four partitions. These controlled data support reproducibility but do not establish performance on arbitrary real-world datasets. Varying Spark local worker settings is not the same as varying partition count.

### Timing and Repetition

The implementation separately records initialization, global clustering, final evaluation, and total pipeline time. The benchmark runner persists and materializes the RDD before timing clustering, reducing the influence of initial data materialization. Each of six configurations used three measured seeds. Results should not be generalized to other hardware without additional testing.

### Convergence Definition

The global K-Means implementation uses **changes in clustering cost (SSE)** as a convergence criterion, with a tolerance of `1e-6` and up to 100 global iterations in the final experiments. This differs from the earlier README statement about maximum squared center movement. The implementation remains a custom interpretation of the paper, not a line-by-line reproduction.

### Conventional K-Means Baseline

A conventional K-Means baseline was evaluated. Because baseline and parallel approaches differ in initialization strategy, clustering-quality comparisons require caution and should not be described as perfectly controlled, apples-to-apples comparisons.

### Additional Evaluation Scope

Partition-count sensitivity and memory measurements must not be described as completed without corresponding evidence. A separate labeled-data evaluation workflow and KDD99 sample results are documented below; this does not establish partition-count sensitivity or memory profiling. Direct numerical comparisons with the reference paper are constrained by different hardware, data, and implementation details.

### RDD Resource Lifecycle

The benchmark framework, rather than the core algorithm, manages persistence and cleanup:

```text
Create input RDD -> Persist -> Materialize -> Run clustering
                 -> Record metadata -> Unpersist
```

Failure-path cleanup is also tested.

### Programming-Language Requirement

The course requires a different implementation language from the selected paper. The paper discusses Spark and references `sklearn`, but the implementation language used in its Spark experiments has not been conclusively established from the verified project materials. Confirm this requirement with the instructor before final submission.
